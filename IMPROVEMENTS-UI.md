# Aurora — UI Improvements

**Analysis date:** 2026-09-28
**Project type:** Multi-page static website — 12 hand-written HTML pages, token-based modular CSS (nine modules in `css/modules/`, built with PostCSS), vanilla ES modules bundled with esbuild, JSON-driven tour and gallery views, service worker, Netlify static hosting
**Analysis mode:** Evidence-based UI improvement review
**Focus:** Project-wide UI

## Improvement overview

The interface rests on a coherent token layer in `css/modules/tokens.css` — type scale, spacing, radii, shadows, layering and light/dark colour values — and on shared surfaces (cards, page hero, utility card, footer) that use it consistently, with reduced-motion handling in place. Every item of the completed development plan and daily audit, archived in `docs/archive/` on 2026-09-28, is closed, and no current plan lists open UI work.

The remaining opportunities are the places where presentation still depends on browser defaults or on per-component choices instead of that shared layer: native controls fall back to the browser's fonts, responsive-image `sizes` declarations are either not applied or do not follow the grid, the button component has no size or variant contract, keyboard focus is styled in about a dozen different ways, and heading and lead sizes are chosen per component. Each proposal keeps the existing visual identity, tokens and page architecture and can be implemented as a separate, focused change.

## Proposed improvements

### IMP-UI-01 — Make native form controls inherit the site typography

- **Status:** COMPLETED — implemented and verified.
- **Affected area:** Every `button`, `input`, `select` and `textarea` that does not set its own font: the project-notice button on all 12 pages, the contact form fields and submit button, the testimonial tabs, the tour filter selects and the gallery filter buttons.
- **Evidence:** `css/modules/base.css:16-24`; `css/modules/components.css:189-205`, `components.css:312-331`, `components.css:386-401`, `components.css:516-530`; `css/modules/subpages.css:273-295`; local workarounds in `css/modules/components.css:681-685`, `css/modules/subpages.css:180-190` and `subpages.css:326-336`; markup in `index.html:416-418`, `index.html:492`, `contact.html:266-331`, `tours.html:187-210`, `gallery.html:184-190`.
- **Current state:** Inter (`--font-base`), `--fs-3` and `--lh-normal` are set on `body` only. Form controls do not inherit font properties by default; only the update-banner buttons and the two thumbnail button classes (`.gallery-item`, `.tour-gallery__button`) restore inheritance locally, and the accordion sets the heading font explicitly. In Chromium at a 1280 px viewport, the project-notice `<button class="btn">` renders in the browser's control font (Arial) at 13.3 px and 31 px high, while `<a class="btn">` renders in Inter at 14.7–16.8 px. On the contact page the inputs and the select render in Arial, the message `textarea` in the browser's monospace font and the submit button in Arial at 13.3 px, under labels set in Inter. The testimonial tabs, the tour filter selects and the gallery filter buttons also render in Arial.
- **Proposed improvement:** Add one base-layer rule that makes `button`, `input`, `select` and `textarea` inherit the page's font properties (family, size and line height), keep component rules only for intentional size changes, and remove the local inheritance workarounds that the base rule makes redundant.
- **Expected value:** Controls use the brand typefaces consistently in both themes, link-based and button-based instances of the same component render alike, and new controls receive the correct typography without per-component patches.
- **Implementation scope:** `css/modules/base.css`, plus a review of control font sizes in `components.css` and `subpages.css` where a component currently relies on the 13.3 px browser default (project-notice and submit buttons). Keep the accordion's explicit heading font, native date, number and select behaviour, checkbox rendering and the existing focus handling.
- **Acceptance criteria:** On all 12 pages the computed `font-family` of every button, input, select and textarea starts with Inter, or with Manrope where a component deliberately sets the heading font; the contact `textarea` no longer uses a monospace font; an `<a class="btn">` and a `<button class="btn">` with the same modifiers have the same font size and height; no rule remains whose only purpose is to restore inherited font properties.
- **Impact:** High
- **Effort:** Small

### IMP-UI-02 — Declare effective, layout-accurate `sizes` for responsive images

- **Status:** COMPLETED — implemented and verified.
- **Affected area:** Tour listing cards, home-page tour cards, the tour detail main image and thumbnails, gallery thumbnails, and the about and contact images.
- **Evidence:** `js/features/gallery.js:4`, `gallery.js:61-66`, `gallery.js:74`; `js/features/tour-detail.js:86-124`; `tours.html:231-255` (same pattern in all six cards); `index.html:297-315`; `about.html:213-240`; `contact.html:198-216`; layout rules in `css/modules/components.css:149-159`, `css/modules/sections.css:177-194`, `css/modules/subpages.css:175-178`, `subpages.css:228-237`, `subpages.css:357-366`, `subpages.css:464-469`, `subpages.css:612-615`.
- **Current state:** In `tours.html`, `gallery.js` and `tour-detail.js` the AVIF and WebP `<source>` elements carry width-described `srcset` values but no `sizes`, so browsers that choose those formats apply the default `100vw` and ignore the `sizes` set on the `<img>`. In Chromium at DPR 1, the first three gallery thumbnails loaded the 1200 w AVIF files (97–184 KB each) for slots of 322–379 px at 1100–1280 px viewports, and their `naturalWidth` (1100) confirms that the `100vw` default was applied. On disk, the 36 gallery images total 5.01 MB at 1200 w, 2.31 MB at 800 w and 0.75 MB at 400 w in AVIF. The values themselves also diverge from the grid: the listing declares `320px` from 900 px for a media column that renders at 460 px from 1024 px; the home tour cards declare `33vw` from 1024 px while the grid keeps two columns until 1280 px (461 px rendered, 363 px declared at 1100 px); the about image declares `100vw` up to 900 px although its column starts at 760 px (231 px rendered at an 800 px viewport); and the tour detail main image and thumbnails share one declaration although they render at 503 px and 363 px at 1280 px.
- **Proposed improvement:** Give every width-described `<source>` the same `sizes` value as its `<img>`, and derive each value from the grid breakpoints and column widths in the canonical CSS, with separate declarations for the tour detail main image and its thumbnails.
- **Expected value:** The browser can select the variant that matches each slot — smaller files for thumbnails and cards, and no under-sized variant where a slot is currently under-declared — using the image variants that already exist.
- **Implementation scope:** `sizes` values in `tours.html`, `index.html`, `about.html`, `contact.html`, `js/features/gallery.js` and `js/features/tour-detail.js`, and the matching expectation in `tests/gallery.test.js:75`. No change to the image pipeline, generated variants, `srcset` candidates, aspect ratios, lazy loading or the hero image priority hints.
- **Acceptance criteria:** Every `<source>` with `w` descriptors has a `sizes` attribute; at 375, 800, 1100 and 1280 px viewports each listed image's effective slot is not smaller than its rendered width and no more than about 25 % larger; at 1280 px and DPR 1 the gallery thumbnails load the 400 w variant; `npm test` passes.
- **Impact:** Medium
- **Effort:** Small

### IMP-UI-03 — Define a size and variant contract for the `.btn` component

- **Affected area:** The shared button component in the hero, the CTA, the home and listing tour cards, the contact form, the project notice, the utility pages (404, thank-you, offline) and the service-worker update banner.
- **Evidence:** `css/modules/components.css:516-564`; contextual overrides in `components.css:132-142`, `components.css:443-448`, `components.css:634-636`, `components.css:681-685` and `css/modules/sections.css:35-38`; undefined modifiers in `tours.html:270`, `tours.html:316`, `tours.html:362`, `tours.html:408`, `tours.html:500` (`btn--secondary`) and `tours.html:454` (`btn--primary`).
- **Current state:** `.btn` defines the gradient style, pill radius and padding but no font size or minimum height, so its size depends on its surroundings, and six contextual selectors set width, font size, padding or minimum height. `.btn--ghost` adds a 1 px border that the base variant does not have. The listing marks five enquiry links `btn--secondary` and one `btn--primary`, but neither modifier exists in CSS, so all six render as the default button. Measured at 1280 px, buttons in seven contexts range from 31 px to 43.2 px in height and from 12.7 px to 16.8 px in text size. Where the container does not stretch them (hero actions at 375 px and 1280 px, utility-page actions at 375 px), the ghost button is 2 px taller than the default button beside it.
- **Proposed improvement:** Define the supported variants (default, ghost and text, plus a secondary variant only if a distinct style is intended) and a small set of size modifiers with a shared minimum height, font size and border box; replace the contextual size overrides with those modifiers and use one defined variant for all listing enquiry links.
- **Expected value:** Paired actions align, classes in markup correspond to real styles, and button sizing is adjusted in one place.
- **Implementation scope:** The button section of `css/modules/components.css`, the contextual rules listed above, and class names in `tours.html`, `index.html`, `contact.html`, the three utility pages and the banner buttons created in `js/script.js:82-91`. Keep the current colour treatment, pill radius, hover lift and the layout widths that belong to a component, such as the two-column tour-card actions. Builds on IMP-UI-01.
- **Acceptance criteria:** Every `btn--*` class used in the pages and in `js/script.js` is defined in CSS; default and ghost buttons of the same size modifier have identical heights in every context at 375 px and 1280 px; no selector outside the button section sets a `.btn` font size, padding or height; the six listing enquiry links share one variant.
- **Impact:** Medium
- **Effort:** Medium

### IMP-UI-04 — Consolidate keyboard focus styling on the focus tokens

- **Affected area:** Keyboard focus presentation of the header controls, navigation links, buttons, tabs, filters, form fields, gallery controls, footer links and legal-page controls.
- **Evidence:** `css/modules/tokens.css:47`, `tokens.css:54`, `tokens.css:80-81`; `css/modules/base.css:7-10`; `css/modules/layout.css:102-107`, `layout.css:174-179`, `layout.css:206-214`, `layout.css:408-412`, `layout.css:463-470`; `css/modules/components.css:210-213`, `components.css:336-340`, `components.css:411-420`, `components.css:531-553`; `css/modules/subpages.css:191-194`, `subpages.css:296-302`, `subpages.css:337-340`; `css/modules/legal.css:144-151`, `legal.css:199-202`.
- **Current state:** The loaded stylesheets contain 36 rules with `:focus` in their selectors and about a dozen distinct treatments: the global 2 px `--primary` outline with a 2 px offset; a 3 px offset on the tabs; the outline removed and replaced by a 2 px box-shadow ring on the menu and theme toggles; the `--focus-ring` shadow on the tour filter selects (its only use, applied on `:focus`); a fixed `rgba(15, 109, 140, 0.22)` ring with a 1 px lift on contact form fields, which keeps the light-theme primary colour in the dark theme; a fixed `rgba(111, 209, 255, 0.55)` outline on the footer contact and social links; and hover-style lifts or shadows applied as focus states on navigation links, `.btn`, `.btn--ghost` and the gallery filters. `--focus-offset` is used in three rules while the other offsets are literal, and `--border-focus` is applied only to the gallery filters, whose border is `none`.
- **Proposed improvement:** Define the focus indicator once as theme-aware tokens — colour, width, offset, and one ring variant for bordered form controls — apply it through the global rule plus that single documented variant, and remove per-component focus colours, literal offsets and focus states that only repeat hover effects.
- **Expected value:** One recognisable focus indicator in both themes, no focus colours that bypass the theme, and fewer component rules to maintain.
- **Implementation scope:** The focus tokens in `css/modules/tokens.css` and the rules listed above. Keep the `:focus-visible` semantics, the skip-link behaviour, the focus management in `js/features/nav.js` and `js/features/lightbox.js`, and the reduced-motion rules; hover styling changes only where it is decoupled from focus. Touches the same button and control rules as IMP-UI-01 and IMP-UI-03.
- **Acceptance criteria:** During keyboard navigation through `index.html`, `tours.html`, `gallery.html`, `contact.html` and one legal page, every focused control shows the shared indicator or the documented form-control variant, with the same geometry in the light and dark themes; no focus rule contains a literal colour value; every focus offset uses `--focus-offset`.
- **Impact:** Medium
- **Effort:** Medium

### IMP-UI-05 — Map headings and running text to shared typographic roles

- **Affected area:** Section and subsection headings, lead paragraphs and running text on the home, about, contact, tour detail, legal and utility pages.
- **Evidence:** `css/modules/tokens.css:12-20`; `css/modules/base.css:42-65`; `css/modules/layout.css:13-15`, `layout.css:343-353`; `css/modules/sections.css:20-27`, `sections.css:136-139`; `css/modules/subpages.css:28-35`, `subpages.css:83-86`, `subpages.css:135-144`, `subpages.css:171-174`, `subpages.css:390-394`, `subpages.css:478-510`; `css/modules/components.css:31-41`; `css/modules/legal.css:28-41`, `legal.css:82-98`; section headers in `index.html:222-225` and `about.html:272-274`.
- **Current state:** The `--fs-1` to `--fs-8` scale is shared, but each component picks its own step. At a 1280 px viewport the same eyebrow-and-`h2` section header renders at 30.4 px/700 on the home page (`.section__title`) and at 23.2 px/600 with a divider on the about page (`.about-section__title`); other `h2` elements render at 23.2 px (contact, CTA, tour gallery) or 18.4 px (legal pages). On the legal pages `h2.legal__title` and `h3.legal__block-title` are both 18.4 px/600. Lead paragraphs (`.hero__lead`, `.page-hero__lead`, `.about-story__lead`, `.legal__lead`) are set to `--fs-2` (14.7 px), below the 16.8 px base paragraph size `--fs-3`; across the CSS modules `--fs-2` is referenced 33 times and `--fs-3` 10 times. Heading dividers are drawn by four separate rules with widths of 32 px, 40 px, 44 px and 100 % and different colours and opacities.
- **Proposed improvement:** Define a small set of roles on top of the existing tokens — page title, section title, subsection title, lead, body and small — as shared classes, or as role tokens where content cannot carry classes; apply them to the existing markup, give the lead role a size at least equal to body text, align the base paragraph size with the size used for running text, and draw the heading divider from one rule.
- **Expected value:** A consistent hierarchy from page to page, visibly distinct heading levels on the legal pages, and fewer per-component font-size declarations.
- **Implementation scope:** `base.css`, `layout.css`, `sections.css`, `subpages.css`, `legal.css`, `components.css` and class names in the affected pages. Headings inside tour descriptions come from `assets/data/tours.json` through a sanitiser that removes classes (`js/features/tour-detail.js:48-75`), so they keep a descendant selector. Keep the heading levels, the Manrope/Inter split, the fluid `clamp()` scale, the home hero and page hero title sizes, and the page copy.
- **Acceptance criteria:** Section headers built from the same pattern render with identical size and weight on every page; on the legal pages the `h2` renders larger than the `h3`; lead text is not smaller than body text at 375 px and 1280 px; component rules no longer set font sizes on text that uses a role; the heading divider is defined once.
- **Impact:** Medium
- **Effort:** Medium

## Selection summary

- The five proposals were selected because each targets a shared system — control typography, image slot declarations, the button component, focus tokens and typographic roles — rather than a single page, affects several pages, and can be verified through computed styles or image selection in a browser. They are ordered by the breadth of the affected interface relative to effort and risk; the order is not based on measured user outcomes.
- IMP-UI-03 builds on IMP-UI-01, because button heights depend on the inherited font size and line height. IMP-UI-04 edits the same control and button rules as IMP-UI-01 and IMP-UI-03 and is simplest to implement after them. IMP-UI-02 and IMP-UI-05 are independent of the others and of each other.
- Every proposal changes files under `css/` or `js/` or pages that the service worker precaches, so shipping any of them follows the workflow in `docs/pipeline-notes.md`: `npm run build` and a raised `VERSION` in `service-worker.js` recorded with `npm run record:sw-bundles`.

## Analysis limitations

- Rendering was inspected in the Chromium-based browser pane of the Claude desktop app on Windows, at DPR 1 and emulated viewports of 375–1280 px, against the unbundled sources served locally. Other browsers and operating systems, high-density screens and the production `dist/` build were not checked; the fallback control font observed (Arial) is platform-specific.
- Focus treatments were inventoried from the rules of the loaded stylesheets, not observed through keyboard traversal.
- No colour-contrast measurements were made, and this report makes no contrast or WCAG claims.
- Image figures are observed source selections and on-disk file sizes, not measured page-load transfer.
- Defect-class observations made during the analysis were left out of this report; they belong in an audit.
