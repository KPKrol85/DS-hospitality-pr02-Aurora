## Recommended workflow

### Local development
1. `npm install`
2. Run `npm run images:bootstrap` once to populate `assets/img-src/`
3. `npm run preview:source` and open `http://127.0.0.1:8181/` (ES modules and `fetch()` do not work over `file://`; see [Local preview](#local-preview)). Work on the source files: the pages load `css/style.css` and `js/script.js` directly, so changes are visible on reload without any build or watch command.
4. The source pages do not register the Service Worker. They unregister a production worker left on the same origin, for example by a `dist/` preview served at the same address; with the default ports the two previews never share an origin.
5. Run `npm run build:images` only after changing raster images in `assets/img-src/`

### Production preview
1. `npm run build`
2. `npm run preview:dist` and open `http://127.0.0.1:8182/` (see [Local preview](#local-preview)).
3. Optionally run `npm run watch:css` and/or `npm run watch:js` to refresh the bundles in `dist/`. HTML and asset changes need another `npm run build`. The production Service Worker serves the bundles cache-first, so bypass it while previewing rebuilt bundles.

### Pre-deployment check and distribution build
1. If you changed raster image sources, run `npm run build:images` first.
2. `npm run predeploy:check` — runs the complete regression suite and then `npm run build`, whatever changed. A failing test stops it before `build` starts and leaves `dist/` untouched. After fixing a failure reported in the steps below, run it again; deploy only the `dist/` of a run that passed.
3. Review failures from:
   - the regression suite (`npm test`; one file reruns with `npm test -- tests/<name>.test.js`)
   - `build:stage`
   - `verify:css`
   - `verify:js`
   - `check:css-assets`
   - `check:assets`
   - `check:assets:dist`
   - `check:csp`
   - `check:csp:dist`
   - `check:tour-catalogue`
   - `check:sw-bundles`
4. When `check:sw-bundles` reports a changed bundle hash and the change is intended, complete the [intentional cache version update](pipeline-notes.md#service-worker-cache-version): it raises `VERSION`, records it with `npm run record:sw-bundles`, and ends with a passing `npm run build`. The check covers only the two bundles, so do the same, without a failing check to prompt it, when another file that the Service Worker caches changes.
5. When `check:csp` reports an inline script without an approved hash, review the script and, if the change is intended, approve it in `_headers` as described in [Content Security Policy for inline scripts](pipeline-notes.md#content-security-policy-for-inline-scripts).

### Deployment
1. Deploy the `dist/` of a passing `npm run predeploy:check` manually to Netlify as the publish directory. It is the complete site root, including `404.html`, `offline.html`, `service-worker.js`, and `_headers`.
2. Do not deploy the repository root: its pages load the unminified sources and do not register the Service Worker.

## Local preview

`scripts/preview-server.js` serves the sources or the built package over HTTP on the local machine. It uses only Node.js built-in modules, is not part of `build`, and is never published, because `build:stage` does not copy `scripts/`.

| Command | Default address | Serves |
|---|---|---|
| `npm run preview:source` | `http://127.0.0.1:8181/` | The maintained sources from the project root |
| `npm run preview:dist` | `http://127.0.0.1:8182/` | The production package `dist/`, as the origin root |

- **Address.** Both servers listen only on the loopback interface `127.0.0.1`, so the preview is not reachable from the local network. `/` serves `index.html`; other pages are requested by file name, for example `/tours.html`. Only `GET` and `HEAD` are answered; other methods receive 405.
- **Port override.** When another project already uses a default port, pass a whole number from 1 to 65535 after `--`: `npm run preview:source -- --port 8281` or `npm run preview:dist -- --port 8282`. An invalid or occupied port ends the command with an error; the server never moves to another port by itself.
- **Stopping.** Press Ctrl+C in the terminal that runs the preview. Both previews can run at the same time, each in its own terminal.
- **Source preview.** Needs no build. It serves only what the maintained pages load (see `preview:source` above); every other path receives a plain 404. It sends no production headers, so the Content-Security-Policy is enforced only in the production preview.
- **Production preview.** Run `npm run build` first; without `dist/`, `dist/index.html`, `dist/404.html`, or a `/*` rule with a Content-Security-Policy in `dist/_headers`, the command ends with an error instead of starting. Every response, the 404 page included, carries each header of the `/*` rule exactly as `dist/_headers` declares it; the preview keeps no policy of its own. A path that matches no file in `dist/`, and `/_headers`, receives the content of `dist/404.html` with status 404. `dist/` and `dist/_headers` are read on every request, so a rebuilt package is served without a restart; while `npm run build` has removed `dist/`, requests receive status 500.
- **Origin isolation.** The default ports give the two previews different origins, so the production Service Worker that the `dist/` preview registers never controls the source preview, and each preview keeps its own `localStorage` (theme, project notice). The browser keeps Service Workers, caches, and storage per origin after the server stops, so a port that previously served another project, or the `dist/` preview through a port override, can still hold that state. The source pages unregister a leftover worker; Clear site data in the browser's developer tools removes the rest.
- **Not a pre-deployment check.** `npm run preview:dist` serves whatever `dist/` currently contains and runs no tests or checks. Deploy only the `dist/` of a passing `npm run predeploy:check`; the preview shows that package in a browser.
- **Limitations.** The preview reproduces static file delivery, the site-wide `/*` headers, and the 404 fallback. It does not reproduce other Netlify hosting features: Netlify Forms processing (submitting the contact form receives 405), the deployed HTTPS environment (the preview uses plain HTTP, where `Strict-Transport-Security` has no effect; Service Workers still work because browsers treat `127.0.0.1` as a secure origin), extensionless URLs and the Pretty URLs post-processing of HTML, compression, and the host's caching headers. `_headers` rules other than `/*` are not applied; the production preview names them at startup. There is no live reload, HTTPS, or proxying.

## Notes
- Source and generated-output ownership is specified in [Source ownership](pipeline-notes.md#source-ownership). Work on the canonical sources: the root HTML pages, `css/style.css` with `css/modules/`, `js/script.js` with `js/features/`, `service-worker.js`, and `assets/`. The production CSS and JS exist only as `dist/css/style.min.css` and `dist/js/script.min.js`, and every `build` recreates `dist/` from scratch.
- `scripts/site-build-contract.js` declares the maintained page inventory and the source-to-production entry tags; adding, removing, or renaming a page or an entry tag starts there (see [Build workflow](pipeline-notes.md#build-workflow)).
- `_headers` and `service-worker-bundles.json` are tracked approval records, not build output: the build reads them and never writes them; only `record:sw-bundles` writes the bundle record. See [Content Security Policy for inline scripts](pipeline-notes.md#content-security-policy-for-inline-scripts) and [Service Worker cache version](pipeline-notes.md#service-worker-cache-version).
- `assets/img-src/` is the source-of-truth directory for raster image inputs.
- `assets/img/` remains the production image directory consumed by HTML, CSS, JS, manifest files, and JSON data.
- Standard `build` and `dist` commands assume `assets/img/` is already up to date.
- The image pipeline preserves relative folder structure and keeps current deterministic file naming.
- The repository uses custom Node scripts in `scripts/` to enforce build integrity and packaging rules.
- `tests/` and `vitest.config.mjs` are development-only: `js/script.js` does not import them and `build:stage` does not copy them, so they never reach `dist/`.
